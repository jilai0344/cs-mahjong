## 0. 结论摘要

1. **现有实现与规格在 13 个点上不同**（D1–D13），其中 6 处是结构性差异（鸟数逐家统计、点炮只赔一家、无封顶、无 B/F 参数、无明细、庄家轮换口径），**不是改几个常数就能对齐的，必须重写计分与结算链路**。
2. **规格第八节的 11 个示例我已用原型函数逐条验算：10 条一致，示例 11 与规格第五节的公式自相矛盾**（见 §4）。这一条必须先裁定，否则测试无法写（示例是要写进测试的）。
3. 现有测试对计分**零覆盖**（只有 2 条扎鸟断言），所以本次重写必须自带表驱动测试，否则无法证明「改对了」。
4. 规格 §九.3（骰子/计分/庄家在服务端）与本项目现状（**还没有服务端**，见 AUDIT R1/P0-1）存在依赖冲突；规格 §九.7（1000 局随机模拟）需要先把牌局推进逻辑从 `App.jsx` 抽出来才能测。这两条各需要你一次授权/裁定（§6 的 S5、S6）。

## 2. 差异清单（D1–D13）

| 编号 | 规格要求 | 现状 | 差异性质 |
|---|---|---|---|
| **D1 基础分** | 小胡 `Base = 2B`；大胡 `Base = 7B × k`（k = 大胡番型个数，线性相加） | 平胡 `1`；大胡 `k × 6`（6 点「番」） | 数值体系全变 + 引入可配参数 B |
| **D2 固定分 F** | 每家应付含 `+2F`，且 `2F` **不参与叠加、不参与翻番、不受封顶** | 不存在 | 新增参数与计算项 |
| **D3 封顶** | `P = min(Base × (n+1), 42B) + 2F`；单家最高 `42B + 2F` | 无封顶 | 新增 |
| **D4 中鸟数 n** | **逐家单独统计**：自摸的有效座位 = {庄位, 该付分者}，三家 n 可能不同 | `hitCount` = 中赢家的鸟数，**三家共用一个倍数** `(1+hitCount)` | **结构性**（必须逐家算） |
| **D5 鸟点→座位** | 以**计分庄位**为基准：1/5/9→庄位、2/6→下家、3/7→对家、4/8→上家 | `drawBirds` 以「赢家」为基准算 offset，语义上等于以胡牌者为庄（本局可对上），但**只标记是否中赢家**，不输出「落在哪个座位」 | 需要输出 `targetSeat` 并按座位匹配（已有 `targetSeat`，可复用） |
| **D6 点炮赔付** | **只有放炮者付 P**，其余两家不付 | 放炮者付 `3X`（包三家），赢家得 `3X` | 金额与责任范围都变 |
| **D7 自摸赔付** | 三家**各自**的 P 相加（各家 n 不同） | 三家各付同一个 `X` | 结构性 |
| **D8 通炮（一炮多响）** | 每位胡牌者按各自 k、n 单独结算，放炮者总付 = ΣP；**通炮时放炮者是庄** | 只结算顺位最近一家 | **结构性**（含交互与仲裁） |
| **D9 庄家轮换** | 胡牌者/触发者是「该次结算的庄」；**通炮时放炮者是庄**；**流局：最后一张牌由谁摸，谁就是庄**；起手胡与中途四喜的结算**不影响下一局庄** | 终局：`dealerId = winnerId` ✓；流局：**顺移 `+1`** ✗；通炮：无 | 流局规则相反；通炮缺失 |
| **D10 起手胡结算** | 每把按**小胡自摸**独立结算（逐家 n + 封顶 + 2F），并在**开局摇骰子**抓鸟 | 每把固定 `2 分/家`，无鸟、无封顶、无 B/F | 计分与抓鸟都变 |
| **D11 中途四喜结算** | 同上（小胡自摸 + 摇骰子），且**每组 4 张各触发一次**、结算后牌局继续、开杠不撤销已结算分 | 固定 `2 分/家`；每组只触发一次 ✓；不打断牌局 ✓ | 计分与抓鸟变 |
| **D12 抓鸟随机源** | 骰子必须**服务端安全随机源**；客户端只放动画 | 客户端 `Math.random()`，且终局从牌墙**头部翻牌** | 依赖服务端（S5）+ 位置待定（S2） |
| **D13 展示与文案** | 结算页逐项：番型与 k、B、F、每家 n 与 n+1、封顶前金额与是否封顶、每家应付、每家得失、骰子结果、新庄；起手胡/中途四喜即时提示不打断；README + 规则页同步（含封顶 42B） | 结算页只有番型标签 + 共用一个倍数的总分 + 4 家得失；弹窗金额硬编码；规则页写「6 番」「每家付 2 分」 | 展示层重做 + 文档同步 |

## 3. 目标设计（抽成独立纯函数模块）

新增 **`src/utils/scoring.js`**（纯函数、无 React、无网络、无随机源），联机服务端就绪后**原样搬入服务端**：

```js
// 鸟点 → 座位（以计分庄位为基准）
seatOfBird(dealerSeat, value)            // (dealerSeat + (value-1)%4) % 4
countBirdsForPayer(birdValues, dealerSeat, payerSeat)  // n：落在 {庄位, 付分者} 的鸟数

// 单家应付
payerAmount({ isBigHu, k, B, F, n })
// → { base, beforeCap, capped, cappedHit, P }   beforeCap=base*(n+1); capped=min(beforeCap,42B); P=capped+2F

// 一次结算（自摸 / 点炮 / 通炮 / 起手胡 / 中途四喜）
scoreRound({
  method, B, F,
  dealerSeat,                    // 该次结算的庄位（胡牌者 / 触发者 / 通炮时的放炮者）
  winnerSeat,                    // 自摸/起手胡/中途四喜
  winners: [{ seat, isBigHu, k }],  // 通炮
  discarderSeat,                 // 点炮 / 通炮
  birdValues: []                 // 鸟点（翻牌牌点 或 骰子点数）
})
// → { changes:[4], details:[{ payer, n, multiplier, base, beforeCap, capped, cappedHit, P }],
//     settlements:[...],  newDealerSeat,  birdDetail:[{value,targetSeat,effectiveFor:[...]}],  zeroSum:true }

// 庄家轮换
nextDealer({ terminal: 'win'|'draw'|'tongpao', winnerSeat, discarderSeat, lastDrawerSeat })
```

**数据结构（供你确认，S13）**——每条明细至少含：
`{ payer, n, multiplier: n+1, base, beforeCap, capped, cappedHit:boolean, P, isBigHu, k, huTypes[] }`。

**庄家状态语义（我按规格如此理解，S12 请确认）**：每局有一个「当前庄」（`dealerId`）；每次结算时用**该次结算的庄位**算 n（起手胡/中途四喜 = 触发者，点炮/自摸 = 胡牌者，通炮 = 放炮者），但**只有终局结果**（胡牌 / 通炮 / 流局）才更新下一局的 `dealerId`。

穷举自检（B=3,F=2，k=1..7 × n=0..4 × 大小胡，共 70 组）：**超出 `42B+2F` 的条数 = 0；封顶截断错误条数 = 0**。

### 示例 11 的矛盾（**必须你裁定，见 S1**）
- 骰子 6 → 下家、3 → 对家；庄位 = 触发者，两颗骰子**都不落在庄位**。
- 按规格第五节「n = 落在 {庄位, 该付分者} 的鸟数」：
  下家 = 1（6 命中自己）、对家 = 1（3 命中自己）、上家 = 0 → `P = 6+6+4 = 16`。
- 规格示例 11 写「对家 n=1+1=2，P=8，共得 18」——多算了 1 只鸟，且与示例 10 的口径（庄位鸟 + 自己鸟）不一致。
- 两种可能：(a) 示例 11 的数字是笔误，应以第五节公式为准（总 16）；(b) 中途四喜的「有效座位」另有含义（例如触发后新增一张「庄位鸟」或该次结算把**触发的那 4 张牌的点数**也算作鸟点）——若如此请给出明确定义。
