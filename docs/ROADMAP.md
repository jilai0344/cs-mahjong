## P0 · 联机安全与稳定（最高优先级）

### P0-1 服务端权威化（架构决策 + 落地）
- **问题**：当前无服务端，房主浏览器即“权威”，洗牌用 `Math.random()`，房主可作弊；公共 MQTT 无鉴权（AUDIT §联机实证）。
- **任务**：把**洗牌、发牌、全部规则判定、算分**迁移到一个服务端进程（Node + `ws`，无框架亦可），客户端只发「意图」（出牌/吃/碰/杠/胡/过/托管），服务端校验后广播。
- **范围**：新增 `server/`（不进前端包）；前端 `utils/multiplayer.js` 改为 WS 客户端适配层。
- **验收**：① 代码中不存在任何客户端侧的洗牌/发牌/胡牌/算分入口被用于联机对局（可用 grep 断言 + 单测）；② 服务端用 `crypto.randomInt` 洗牌；③ 客户端收到的消息中不含他人手牌与牌墙内容（见 P0-2 断言）；④ 单机模式完全不依赖服务端。
- **依赖**：Q8（规则归属）；**另需你裁定**：服务端部署位置（自建 VPS / 云主机 / 云函数）与「单机保持纯静态、仅联机需要服务端」的双形态是否接受。

### P0-2 信息隔离与不可作弊
- **验收**：① 服务端**按座位裁剪**消息，一局 4 个客户端的完整收发日志中，任意客户端收到的载荷不含其他座位手牌/牌墙顺序（写一个断言脚本，跑 50 局验证）；② 客户端伪造 `fromSeatId` 无效（服务端按连接绑定座位，忽略载荷中的座位字段）；③ 出牌/吃碰杠胡必须服务端校验：非本人回合、手中无该牌、选项不合法一律拒绝并记录。

### P0-3 会话鉴权与房间安全
- **验收**：① 加入房间需要服务端签发的座位令牌（token），第三方无法仅凭房间号订阅他人频道；② 房间号从 4 位提升为 ≥6 位或“6 位数字 + 校验位”，并支持邀请链接；③ 单 IP 房间/连接数限流；④ 关键事件（加入/离开/操作）落地日志，可用于复盘作弊。

### P0-4 稳定性：断线重连 / 心跳 / 超时 / 幂等
- **验收**：① 断线 30s 内重连可**保留座位并恢复完整对局**（服务端下发全量快照：手牌、面子、弃牌、当前轮到谁、剩余牌墙数、分数）；② 掉线立即进入**托管**（AI 代打），回来后自动解除托管；③ 所有下行消息带单调递增 `seq`，客户端重放/乱序自动丢弃；④ 客户端超时未响应时服务端**代为“过”**并推进（彻底消除卡死）；⑤ 房主退出后房间不崩溃（房主无特权或支持房主迁移）；⑥ 服务重启后按房间快照恢复或明确告知玩家房间已结束。
- **验收补充**：4 个模拟客户端跑完整局，含“同时抢胡/碰/杠”与随机断线重连，**连续 500 局无状态分叉、无卡死**（脚本化，CI 可跑，输出最终哈希一致）。

### P0-5 客户端响应窗口超时兜底（单机也要修）
- **现状**：本地玩家面对吃/碰/杠/胡提示不操作 → 整局永久卡死（无人能推进）。
- **验收**：出现响应提示后 15s 自动「过」并继续；测试用例覆盖（可用抽取出的状态机做单测，或 Playwright E2E）。

### P0-6 联机冒烟：4 客户端 1 局可玩闭环
- **验收**：房主建房 → 3 人加入 → 准备/开局 → 完整打完一局（含吃碰杠胡）→ 结算页四方一致 → “再来一局”正常。

## P1 · 规则 Bug 与测试基建

### P1-1 含杠手牌的胡牌资格（Q1）
- **验收**：`checkHu` 支持 0/1/2/3/4 个杠面子（1 个杠按 3 张有效牌折算），新增单测：手牌 10+暗杠 4 张可胡；杠上开花可触发；杠上炮可触发；连续两个杠（15→16 张）可胡。

### P1-2 一炮多响与跨玩家优先级（Q9）
- **验收**：① 优先级严格为 胡 > 杠 > 碰 > 吃，且**胡优先于任何吃碰杠**（含本地座位与 AI）；② 一炮多响：多家同时胡时按各自番型分别结算，分数总和守恒（写守恒断言）；③ 回归：本地真人可碰的牌不会吞掉 AI 的胡。

### P1-3 抢杠胡 / 海底捞月 / 海底炮（Q11）
- **验收**：补杠时向其他三家发起抢胡窗口（超时视为放弃）；牌墙最后一张牌触发海底番种；两项均有单测；若无此项需求则删除死代码并同步 README。

### P1-4 扎鸟取牌与结算（Q4/Q5）

### 实际路由（已生效）

子代理不再走降级的全局 delegation，已改为 **profile 级**、指向 AgentPlan 前沿模型（`~/.hermes/profiles/wxbot/config.yaml`）：

```
delegation.provider = custom
delegation.base_url = https://ark.cn-beijing.volces.com/api/plan/v3
delegation.api_mode = codex_responses
delegation.model    = deepseek-v4-pro
```

回滚：`hermes --profile wxbot config set delegation.model deepseek-v4-flash`（再 `unset delegation.provider/base_url/api_mode/api_key` 即回落全局配置）。

> `delegate_task` **一次调用内所有子代理共用同一个 `delegation.model`**。要按工作流使用不同前沿模型，两条路：
> ① 该批任务前先 `hermes --profile wxbot config set delegation.model <前沿模型>`；
> ② 以子进程方式跑专项任务：`hermes --profile wxbot -m kimi-k3 -q "<任务>"`（已实测 `hermes --profile wxbot -m deepseek-v4-pro -z "…"` 正常返回）。
> 主会话（orchestrator）当前仍是 `model.default = deepseek-v4.1-flash`；要一并提到前沿只需一条命令 `hermes --profile wxbot config set model.default deepseek-v4-pro`，**需你确认**（会改变本会话后续所有回合）。
> **读图通道**：本机没有任何可读图的模型通道，`delegate_task` 子代理只能文本工作 → 「UI 视觉」工作流只能是「代码 + 人工看截图」验收；若要真多模态评审，需要你提供一个能读图的模型/通道。
